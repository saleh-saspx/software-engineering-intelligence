# راهنمای استفاده از Software Engineering Intelligence

نسخهٔ 1.2.0 · [English guide](usage-guide.en.md)

Software Engineering Intelligence یک اسکیل (Skill) برای Claude است که مثل یک همکار ارشد مهندسی
نرم‌افزار کار می‌کند: تغییرات را پیاده‌سازی و خودش بازبینی می‌کند، کد و Pull Request را بازبینی
می‌کند، مخزن کد و معماری را ارزیابی می‌کند، الگوهای طراحی را ارزیابی، انتخاب و بازبینی می‌کند،
مایگریشن‌های پایگاه داده را بررسی می‌کند، راهبرد تست می‌نویسد، مدل‌سازی تهدید انجام می‌دهد، بدهی
فنی را اولویت‌بندی می‌کند، با خیال راحت بازآرایی (refactoring) می‌کند و ADR می‌نویسد. این راهنما
توضیح می‌دهد اسکیل را چطور نصب کنید، کارتان را چطور بخواهید و خروجی را چطور بخوانید.

## ۱. نصب و به‌روزرسانی

### اپ‌های Claude (claude.ai در مرورگر و اپ دسکتاپ)
پیش‌نیاز: پلن Pro، Max، Team یا Enterprise، و روشن‌بودن گزینهٔ **Code execution and file creation**
در **Settings > Capabilities**. در پلن‌های Team و Enterprise ممکن است مدیر سازمان اول باید Skills
را برای سازمان فعال کند.

1. فایل `dist/software-engineering-intelligence.zip` را از همین مخزن (یا از نسخهٔ محلی‌تان) بردارید.
2. به **Settings > Capabilities** بروید و پایین صفحه به بخش **Skills** برسید.
3. روی **Upload skill** بزنید و فایل ZIP را انتخاب کنید. فایل را دست‌نخورده آپلود کنید؛ پوشهٔ اسکیل
   در ریشهٔ آن است.
4. مطمئن شوید اسکیل در فهرست روشن است.

**به‌روزرسانی:** نسخهٔ قبلی را از فهرست Skills حذف کنید و بعد ZIP جدید را آپلود کنید. اسکیل‌های
سفارشی مال یک حساب کاربری‌اند؛ هر نفر باید نسخهٔ خودش را آپلود کند.

### Claude Code
- **به‌صورت پلاگین از همین مخزن** (به‌روزرسانی از طریق git):
  ```
  /plugin marketplace add saleh-saspx/software-engineering-intelligence
  /plugin install software-engineering-intelligence@software-engineering-intelligence
  ```
  اگر مخزن خصوصی است، سیستم باید به آن دسترسی git داشته باشد (مثلاً با `gh auth login`). برای
  به‌روزرسانی بعدی:
  `claude plugin update software-engineering-intelligence@software-engineering-intelligence`
  — مارکت‌پلیس‌های غیر از Anthropic تا خودتان روشن نکنید خودکار به‌روز نمی‌شوند.
- **به‌صورت اسکیل شخصی:** پوشهٔ `skills/software-engineering-intelligence/` را در
  `~/.claude/skills/software-engineering-intelligence/` کپی کنید. برای یک پروژهٔ خاص، آن را در
  `.claude/skills/` همان مخزن بگذارید و commit کنید.
- **بررسی نصب:** دستور `/skills` باید آن را نشان دهد. برای فراخوانی مستقیم:
  `/software-engineering-intelligence` (اسکیل شخصی) یا
  `/software-engineering-intelligence:software-engineering-intelligence` (پلاگین).

### Claude API
همان فایل ZIP را با Skills API آپلود کنید —
[راهنمای Skills](https://platform.claude.com/docs/en/build-with-claude/skills-guide) و
[endpoint ساخت اسکیل](https://platform.claude.com/docs/en/api/skills/create) را ببینید.

### برای اسکریپت‌ها
Python نسخهٔ 3.9 یا بالاتر (فقط کتابخانهٔ استاندارد) و `git` برای تحلیل تاریخچهٔ تغییرات. اسکیل
بدون اسکریپت‌ها هم کار می‌کند؛ اسکریپت‌ها اندازه‌گیری و سرنخ اضافه می‌کنند.

## ۲. اسکیل کی فعال می‌شود
- **خودکار:** وقتی از Claude می‌خواهید کد، اسکیما یا سیستمی را بازبینی، ممیزی، ارزیابی، بازآرایی،
  تمیز، مقاوم، تست یا طراحی کند؛ الگوی طراحی‌ای را انتخاب، بازبینی یا حذف کند؛ یا تغییری غیرساده را
  پیاده‌سازی کند. Claude کدی را هم که خودش نوشته با این اسکیل بازبینی می‌کند. لازم نیست اسم روشی را
  بیاورید.
- **با درخواست شما:** اسمش را بیاورید («با اسکیل software-engineering-intelligence این کار را بکن»)
  یا در Claude Code دستور اسلشی را که بالا آمد بزنید.
- **هر زبانی:** فارسی یا انگلیسی بنویسید؛ پاسخ به زبان شما می‌آید (اصطلاحات فنی ممکن است انگلیسی
  بمانند).

## ۳. تعیین عمق کار
اسکیل عمق کار را با ریسک آن تنظیم می‌کند. بگویید چقدر عمیق می‌خواهید:

| می‌خواهید | مثلاً بگویید | چه می‌گیرید |
|---|---|---|
| یک تغییر کوچک یا جواب کوتاه | «چک null در `parse_date` رو درست کن»، «الگوی outbox چیه؟» | خود تغییر و نتیجهٔ اجرای تست، یا جوابی کوتاه (حدود ۸۰ کلمه) |
| یک نگاه سریع | «قبل از merge یه نگاه سریع به `handler.go` بنداز» | بازبینی سبک: نتیجه و چند یافتهٔ مهم (تا حدود ۴۰۰ کلمه) |
| یک کار معمولی | «این PR رو بازبینی کن»، «صفحه‌بندی `/orders` رو پیاده کن»، «`calculate_shipping` رو refactor کن» | گردش‌کار مناسب و گزارشی ساختارمند (معمولاً ۶۰۰ تا ۱۵۰۰ کلمه) |
| یک ارزیابی عمیق | «این ریپو رو ارزیابی کن و یه backlog اولویت‌بندی‌شده بده»، «webhook پرداخت رو threat model کن» | خلاصهٔ مدیریتی، جدول ریسک یا backlog، یافته‌ها با دامنهٔ مشخص، و این‌که چه چیزی بررسی شد و چه چیزی نه |

بخش‌های پرریسک — احراز هویت، پرداخت، مایگریشن روی جدول‌های بزرگ، هم‌روندی، APIهای عمومی و نقاط
توسعه، مرز اعتماد جدید، وابستگی جدید، قابلیت‌های مبتنی بر LLM — تحلیل را عمیق‌تر می‌کنند، نه پاسخ را
طولانی‌تر. هر وقت جواب کوتاه خواستید، بگویید «کوتاه».

## ۴. چه اطلاعاتی بدهید
- **کد:** مخزن، پوشه، فایل یا diff. در Claude Code پوشهٔ کاری‌تان را می‌خواند؛ در اپ‌ها فایل‌ها (یا
  یک ZIP) را آپلود کنید یا متن را بچسبانید.
- **هدف و تصمیمی که پیش رو دارید:** «فصل بعد صورتحساب اشتراکی رو شروع می‌کنیم»، «امشب merge
  می‌کنیم».
- **محدودیت‌ها:** ADRها، قراردادهای تیم، ضرب‌الاجل، الزامات انطباق، «این فقط نمونهٔ اولیه است».
- **چیزهایی که خودش نمی‌بیند:** اندازهٔ جدول‌ها و نرخ نوشتن، ترافیک، شیوهٔ استقرار (rolling
  deploy؟)، تست‌هایی که در CI اجرا می‌شوند.
- **خروجی دلخواه:** فقط یافته‌ها، اعمال اصلاحات، برنامهٔ کار، ADR یا جواب کوتاه.

| کار | نمونه درخواست | چه اتفاقی می‌افتد |
|---|---|---|
| پیاده‌سازی و خودبازبینی | «صفحه‌بندی رو برای `/api/orders` پیاده کن و تغییر خودت رو هم بازبینی کن.» | قدم‌های کوچک، نوشتن و اجرای تست، بعد خودبازبینی با چک‌لیست |
| بازبینی Pull Request | «این PR رو قبل از merge بررسی کن — endpoint استرداد وجه رو اضافه می‌کنه.» | نتیجهٔ بازبینی و یافته‌ها به ترتیب شدت؛ اول درستی و امنیت |
| بازبینی سریع | «قبل از push یه نگاه سریع به `handler.go` بنداز.» | قالب سبک: چند خط، موارد مسدودکننده در ابتدا |
| ارزیابی مخزن | «معماری و بدهی فنی این ریپو رو ارزیابی کن — فصل بعد صورتحساب اشتراکی رو شروع می‌کنیم.» | شناسایی مخزن، نقاط داغ تغییر، چرخه‌های وابستگی، پروفایل کیفیت، backlog مرتب |
| تصمیم معماری | «لیدمون می‌خواد این سرویس رو ببره سمت معماری hexagonal. می‌ارزه؟» | تناسب با شرایط، گزینه‌ها با هزینه‌شان، توصیه و در صورت نیاز ADR |
| ADR | «برای مهاجرت از REST polling به webhook یه ADR بنویس.» | ADR از روی قالب: زمینه، گزینه‌ها، تصمیم، پیامدها |
| الگوهای طراحی | «کدوم الگوهای طراحی تو `src/` استفاده شدن و کدوم‌ها غلط به کار رفتن؟» | بخش ۶ را ببینید |
| پایگاه داده و مایگریشن | «امشب migration 0042 رو اجرا می‌کنیم — جدول `orders` چهل میلیون ردیف داره. نگرانی‌ای هست؟» | ریسک قفل و بازنویسی جدول، سازگاری با کدی که هنوز در حال اجراست، برنامهٔ مرحله‌به‌مرحله |
| راهبرد تست | «تست‌هامون باگ‌های واقعی رو نمی‌گیرن — برای بازنویسی checkout یه راهبرد تست پیشنهاد بده.» | ارزیابی مجموعهٔ تست و برنامهٔ تأیید و اعتبارسنجی مبتنی بر ریسک |
| بدهی فنی | «کدوم بخش‌های این کد رو اول refactor کنیم؟» | نقاط داغ در برابر نقشهٔ راه؛ دفتر ثبت بدهی فنی |

| بازبینی امنیتی | «کد احراز هویت و آپلود فایل رو از نظر امنیتی بازبینی کن.» | یافته‌های مبتنی بر OWASP با ردگیری مسیر داده از ورودی تا نقطهٔ خطر |
| مدل‌سازی تهدید | «قبل از ساخت، طراحی جدید webhook پرداخت رو threat model کن.» | دارایی‌ها، مرزهای اعتماد، تهدیدهای رتبه‌بندی‌شده، راهکارهای قابل تست |
| توسعه‌پذیری | «مشتری‌ها می‌خوان فرمت خروجی خودشون رو اضافه کنن — سیستم پلاگین بسازیم؟» | نقاط تغییر مبتنی بر شواهد، قراردادهای منتشرشده، جداسازی |

## ۶. الگوهای طراحی
نسخهٔ 1.2 توانایی قضاوت دربارهٔ ۲۲ الگوی طراحی کلاسیک (ایجادی، ساختاری و رفتاری، مطابق کاتالوگ
Refactoring.Guru) را اضافه کرده است. چهار نوع درخواست:

- **ارزیابی** — «الگوهای طراحی این سرویس رو دربیار و بگو کدوم‌ها غلط به کار رفتن.» برای هر مورد یک
  ردیف می‌گیرید: الگو، اجزایش (کدام کلاس چه نقشی دارد)، نیرویی که حل می‌کند، رأی — موجه، بد اجراشده،
  بی‌دلیل یا با نام اشتباه — شواهد و اقدام پیشنهادی.
- **انتخاب** — «برای وضعیت سفارش‌ها Strategy بهتره یا State — یا هیچ‌کدوم؟»، «این پیشنهاد تیمه؛ چی
  بسازیم؟» پاسخ مسئله و نیروی اصلی را می‌گوید، ساده‌ترین راه‌حل بدون الگو، گزینه‌ها و الگوهای شبیه
  به آن‌ها، هزینه (تعداد نوع‌ها، لایه‌های واسط، سیم‌کشی، تست)، این‌که چه چیزی ساده‌تر و چه چیزی
  سخت‌تر می‌شود، و کی باید تصمیم را دوباره بررسی کرد. **«بدون الگو» هم پاسخ معتبری است.**
- **بازآرایی به‌سمت یک الگو یا دور شدن از آن** — «این زنجیرهٔ if/elif رو جوری بازآرایی کن که اضافه‌کردن
  کشور جدید امن باشه.» اول تست‌های مشخصه‌ساز نوشته می‌شود، ارزان‌ترین ساختار برنده است (اغلب یک
  dict از توابع یا داده‌ای ساده)، رفتار حفظ می‌شود، و ایرادهایی که در مسیر پیدا می‌شوند جداگانه
  گزارش می‌شوند، نه این‌که بی‌صدا تغییر کنند.
- **بازبینی پیاده‌سازی** — «زنجیرهٔ decorator دور HTTP client رو بازبینی کن.» اجزا، سیم‌کشی و ترتیب
  آن، تست‌های قراردادی مشترک برای همهٔ پیاده‌سازی‌ها، رفتار در خطا، و پوشش همهٔ مسیرها توسط
  wrapperهای امنیتی بررسی می‌شود.

نکته: بگویید چه چیزی زیاد تغییر می‌کند («هر فصل یه نوع تخفیف اضافه می‌کنیم») — الگو را تغییری
توجیه می‌کند که جذب می‌کند. فریم‌ورک‌تان را بگویید: سازوکارهای Spring، Laravel، Go، Python و
TypeScript/React بر اساس کاری که واقعاً می‌کنند توصیف می‌شوند. برای ثبت تصمیم، قالب pattern-decision
را بخواهید.

## ۷. خواندن نتیجه
- **دامنه و بررسی‌ها:** چه چیزهایی خوانده شد، سرسری دیده شد یا کنار ماند؛ کدام دستورها اجرا شد و
  نتیجه‌شان — یا «اجرا نشد» و دلیلش.
- **نتیجهٔ بازبینی:** approve (تأیید) · approve with suggestions (تأیید با پیشنهاد) ·
  changes requested (نیاز به تغییر) · blocked (مسدود).
- **یافته‌ها** این شکلی‌اند:
  ```
  - [major · likely] src/orders/service.py:42 — what is wrong and why it matters. Fix: … (DATA-TXN-03)
  ```
  وقتی فارسی بنویسید، متن یافته هم فارسی می‌آید؛ برچسب‌ها همین معناها را دارند.
- **شدت:** blocker (قبل از merge یا انتشار باید رفع شود) · major (جدی) · minor (جزئی) ·
  nit (سلیقه‌ای؛ هیچ‌وقت مانع نمی‌شود).
- **اطمینان:** confirmed (اجرا، بازتولید یا کامل ردگیری شده) · likely (شواهد ایستای محکم) ·
  possible (نیاز به بررسی).
- **نوع:** نقص (defect)، آسیب‌پذیری، ریسک پایداری، کارایی، بدهی فنی، ریسک معماری، کمبود تست،
  بده‌بستان آگاهانه (trade-off)، محدودیت سیستم قدیمی، نقص بی‌اهمیت، پرسش. فقط مشکلاتی که هزینهٔ تغییر
  را بالا می‌برند «بدهی فنی» نامیده می‌شوند.
- **شناسهٔ قاعده‌ها** مثل `DES-PAT-01` برای ردگیری‌اند. برای دیدن متن قاعده:
  `python3 <skill-dir>/scripts/rules.py show DES-PAT-01`
- **کارهایی که نمی‌کند:** ادعای پاس‌شدن تست بدون اجرای آن؛ «امن» یا «بدون باگ» خواندن کد؛ ساختن API،
  نسخه یا CVE از خودش؛ و کار تخریبی (حذف داده، مایگریشن روی production، force push) بدون تأیید شما.

## ۸. اسکریپت‌ها
اسکریپت‌های Python با کتابخانهٔ استاندارد در پوشهٔ `scripts/` اسکیل. Claude هر وقت جواب سؤالی را
بدهند اجرایشان می‌کند؛ خودتان هم می‌توانید اجرا کنید. خروجی‌شان **سرنخ و اندازه‌گیری است، نه حکم**.
همه `--help` دارند و بیشترشان `--json`.

| اسکریپت | کاربرد |
|---|---|
| `repo_survey.py PATH` | نگاه اول: زبان‌ها، فریم‌ورک‌ها، اندازه، تست‌ها، CI، مایگریشن‌ها، مستندات، فایل‌های پرخطر commitشده |
| `hotspots.py PATH --since "12 months"` | رتبه‌بندی فایل‌ها بر اساس تعداد تغییر × پیچیدگی |
| `deps.py PATH --forbid "domain->infra"` | گراف وابستگی ماژول‌ها، چرخه‌ها، ناپایداری، جهت‌های ممنوع |
| `security_scan.py PATH` | سرنخ‌های امنیتی با شناسهٔ قاعده و ارجاع OWASP |
| `migration_lint.py PATH --git-base REF` | ریسک قفل و استقرار در مایگریشن‌های SQL، Laravel، Rails، Django و Alembic |
| `test_smells.py PATH` | تست‌هایی که نمی‌توانند شکست بخورند یا قابل اعتماد نیستند |
| `pattern_scan.py PATH` | فهرست الگوهای طراحی و سرنخ‌های استفادهٔ نادرست (Java، Kotlin، C#، PHP، TS/JS، Python، Go) |
| `rules.py list/show/search` | جست‌وجوی قاعده‌ها |
| `check_report.py REPORT.md` | بررسی گزارش نوشته‌شده از نظر دامنه، شواهد و قالب یافته‌ها |
| `validate_skill.py` | خودآزمایی اسکیل |

نمونه (نصب شخصی در Claude Code):
```
python3 ~/.claude/skills/software-engineering-intelligence/scripts/pattern_scan.py path/to/repo
python3 ~/.claude/skills/software-engineering-intelligence/scripts/hotspots.py . --since "12 months"
```

## ۹. قالب‌ها
گزارش را با اسمش بخواهید — «به‌صورت ADR بنویسش»، «یه برنامهٔ مایگریشن بده»:
گزارش بازبینی · گزارش ارزیابی · آیتم و دفتر بدهی فنی · ADR · برنامهٔ بازآرایی · توصیف معماری ·
مدل تهدید · راهبرد تست · برنامهٔ مایگریشن · تصمیم الگوی طراحی (pattern decision).
قالب‌ها فقط می‌گویند چه چیزهایی *می‌تواند* بیاید؛ بخش‌های خالی حذف می‌شوند.

## ۱۰. نکته‌ها
- **تصمیم را بگویید، نه فقط کد را** — «امشب منتشرش کنیم؟» بازبینی را متمرکز می‌کند.
- **مرحلهٔ پروژه را بگویید** — «نمونهٔ اولیه»، «سرویس پرداخت تحت نظارت»: سطح سخت‌گیری با آن عوض
  می‌شود.
- **اصلاح را صریح بخواهید** — «اصلاح دو یافتهٔ اول رو اعمال کن و تست‌ها رو اجرا کن».
- **روی یک یافته عمیق شوید** — «یه تست شکست‌خورنده بنویس که یافتهٔ دوم رو بازتولید کنه».
- **مخالفت کنید** — «این واقعاً تو Laravel مشکله؟» باعث می‌شود شرایط را دوباره بسنجد؛ اگر شواهد
  بگوید، نظرش را عوض می‌کند.
- **مخزن‌های بزرگ را محدود کنید** — به ماژولی اشاره کنید که به تصمیم‌تان مربوط است.
- **طول جواب را تعیین کنید** — «کوتاه» یا «ارزیابی کامل».
